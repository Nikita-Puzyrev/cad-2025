# Лабораторная работа №3. Spring Security

**Цель работы:** получить практические навыки работы с Spring Framework
(модуль Spring Security).

## 1. Теоретические сведения

Spring Security — фреймворк обеспечения безопасности приложений на Spring.
Основные возможности:

- **аутентификация** — проверка подлинности пользователя;
- **авторизация** — определение прав доступа для ролей и контроль доступа к
  защищённым ресурсам;
- **защита от атак** — CSRF-защита, фильтрация и валидация входных данных,
  защита от подбора паролей;
- **управление сеансами** — стратегии продолжительности сеанса, работа с
  токенами.

Защита строится из настройки правил аутентификации, правил авторизации,
защиты от атак и управления сеансами.

## 3. Настройка безопасности

Класс `SecurityConfig` объявляет хранилище пользователей в памяти, кодировщик
паролей BCrypt и цепочку фильтров:

```java
@Configuration
@EnableWebSecurity
@EnableMethodSecurity(prePostEnabled = true)
public class SecurityConfig {

    @Bean
    public InMemoryUserDetailsManager userDetailsService(PasswordEncoder encoder) {
        UserDetails user = User.withUsername("user")
                .password(encoder.encode("password")).roles("USER").build();
        ...
        return new InMemoryUserDetailsManager(guest, user, moderator, admin);
    }
}
```

Все страницы, кроме формы входа, требуют аутентификации; вход выполняется через
стандартную форму Spring Security, выход — через `/logout`. Пароли хранятся в
закодированном виде (`BCryptPasswordEncoder`), а не в открытом тексте, как в
примере из методических указаний.

Разграничение прав реализовано аннотациями `@PreAuthorize` на методах
контроллера:

```java
@PreAuthorize("hasAnyRole('USER', 'MODERATOR', 'ADMIN')")
@PostMapping("/addTask")
public String addTask(@ModelAttribute Task task) { ... }

@PreAuthorize("hasAnyRole('MODERATOR', 'ADMIN')")
@GetMapping("/deleteTask/{id}")
public String deleteTask(@PathVariable Long id) { ... }

@PreAuthorize("hasRole('ADMIN')")
@PostMapping("/addCategory")
public String addCategory(@RequestParam String name) { ... }
```

## 4. Роли и права

| Роль | Логин | Права |
|---|---|---|
| GUEST | `guest` | только просмотр списка задач |
| USER | `user` | просмотр и добавление задач |
| MODERATOR | `moderator` | дополнительно изменение статуса и удаление задач |
| ADMIN | `admin` | дополнительно управление категориями |

Пароль для всех учётных записей — `password`.

## 5. Дополнительное задание

Требовалось добавить одну-две роли, использующие функционал предыдущей работы.
Добавлены две роли:

- **GUEST** — роль «только чтение»: просмотр списка задач без возможности
  изменения данных;
- **ADMIN** — роль администратора справочника: помимо прав модератора управляет
  категориями задач (функционал лабораторной работы №2) — добавление новых
  категорий.

Интерфейс подстраивается под роль: форма добавления задач скрыта от GUEST,
колонка «Действия» и форма управления категориями отображаются только
соответствующим ролям (`sec:authorize` в шаблоне). Серверная проверка при этом
остаётся основной защитой: даже при ручном формировании запроса сервер
возвращает 403.

Проверка реальными запросами к запущенному приложению (вход через форму с

| № | Действие | Результат |

| 4 | Интерфейс роли MODERATOR | отображается колонка «Действия» |
| 5 | Интерфейс роли ADMIN | дополнительно отображается форма добавления категории |
| 6 | USER: `POST /addTask` | перенаправление на `/`, задача добавлена |
| 7 | USER: `GET /deleteTask/1` | **403 Forbidden** |
| 8 | USER: `POST /addCategory` | **403 Forbidden** |
| 9 | MODERATOR: `GET /deleteTask/1` | 200, задача удалена |
| 10 | MODERATOR: `POST /addCategory` | **403 Forbidden** |
| 11 | ADMIN: `POST /addCategory` («Спорт») | перенаправление на `/` |

отклоняются (403): формы в шаблоне используют `th:action`, поэтому Thymeleaf
автоматически вставляет скрытое поле `_csrf`.

## 7. Выводы

Изучены механизмы Spring Security: аутентификация по форме входа, хранение
пользователей в памяти, кодирование паролей, авторизация на уровне методов с
помощью `@PreAuthorize`, защита от CSRF и управление сеансами. В приложение из
лабораторной работы №2 добавлены четыре роли с разными правами: GUEST (только
просмотр), USER (добавление задач), MODERATOR (изменение статуса и удаление),
ADMIN (управление категориями). Права проверяются дважды — на сервере
(аннотации) и в интерфейсе (`sec:authorize`), при этом серверная проверка
является основной. Написаны шесть автоматизированных тестов, проверяющих
перенаправление на форму входа, ограничения для каждой роли и доступность
страницы входа.
